# Contradiction Halt Rule

## Principle: the request can be wrong — surface it, don't silently "fix" it

The user (or a task, plan, or ticket) may ask for something that contradicts these rules, the
established architecture, or that would introduce a bug. **The user may be wrong, and that is
expected.** When you detect such a contradiction, **stop and tell the user, and do nothing else about
it** until they decide.

This applies whether the contradiction is with:

- a rule in `.claude/rules/*.md` or `CLAUDE.md`,
- the documented architecture or an existing pattern — the `handler.go` → `service.go` →
  `internal/repositories/*` layering, constructor injection wired in `internal/bootstrap/bootstrap.go`,
  repository interfaces in `internal/repositories/interfaces.go`, config read only through
  `internal/config`,
- a latent bug the requested change would create or depend on, or
- a security / access-control invariant — `middleware.Auth()` before every guard,
  `guards.Permission` / `guards.Role` on every `/settings` route, the `type` claim check that keeps
  refresh tokens out of the access path, the `status = 'active' AND deleted_at IS NULL` check behind
  every authenticated request, bcrypt for passwords, SHA-256 at rest for one-time tokens, and the
  sort/filter allow-lists in each repository.

## What "do nothing" means

- **Do not implement the contradicting change**, not even a best-guess partial version.
- **Do not silently work around it** or quietly pick a different approach without saying so.
- **Do not fix the contradicting bug on your own initiative** as part of an unrelated task — report
  it and wait.

## What to do instead

1. State the contradiction plainly: what was requested, which rule / pattern / invariant it conflicts
   with (cite the rule file or `file:line`), and the concrete consequence.
2. If you have a compliant alternative, offer it as a recommendation — but still let the user choose.
3. Proceed once the user confirms. If they confirm the original request knowing the trade-off, that
   is their call, and you implement it in full.

## Scope

- This is a **halt-and-report** rule, not permission to refuse work.
- It does **not** apply to trivial style nits — match the surrounding code and move on.
- It does not license scope creep either: noticing an unrelated defect means *reporting* it, not
  fixing it inside the current change.

## Invariants and known sharp edges

- **Migrations run on server boot** (`postgres.Migrate()` in `cmd/server/main.go`) and also via
  `go run ./cmd/migrate`. An applied migration is never edited; a change is a new numbered pair.
- **The `superuser` role is load-bearing.** Both guards bypass for it, `roles.name` is UNIQUE so the
  bypass cannot be claimed by a look-alike role, and the role cannot be renamed or deleted (422).
- **The `.agents/skills/` bundle is vendored.** `.claude/skills` is a symlink to it. Do not edit it as
  part of unrelated work.
- **There are no tests yet.** `make test` runs `go test ./...` and finds no `_test.go` files. Do not
  cite a test as evidence that something is safe.
- **`docs/swagger.json` is generated by swag** and may lag the code until `make docs` is run.
